# Foundation

The Foundation collection contains the core institutional, architectural and operational documents that established the initial structure of the InfraDev Academy.

It preserves the project principles, scope, Governance foundations, review evidence and release-level decisions that made the ecosystem ready for continued development.

---

## Purpose

This collection exists to document the initial base of the InfraDev Academy.

It supports:

- institutional clarity;
- project identity;
- architectural consistency;
- Governance;
- review traceability;
- release readiness;
- contributor orientation;
- long-term continuity.

The Foundation collection explains how the project began, what it established and which principles continue to guide its evolution.

---

## Scope

The collection may contain documents related to:

- Foundation Charter;
- Project Manifesto;
- initial project scope;
- repository architecture;
- document architecture;
- Governance structure;
- review Frameworks;
- Sprint 0 Review;
- release validation;
- Foundation certification;
- initial Roadmap;
- foundational decisions.

The Foundation collection should not become a general-purpose archive.

Documents should remain here only when they define or preserve the original project base.

## Foundation as a Project Stage

The Foundation stage represents the period in which the InfraDev Academy established the minimum structure required to evolve responsibly.

This stage focused on:

- defining the project purpose;
- creating the repository architecture;
- establishing document families;
- defining collaboration principles;
- documenting architectural decisions;
- creating review processes;
- validating the initial project state;
- preparing the first release.

The Foundation stage was not intended to produce the complete Academy.

It was intended to create the conditions for future work to remain structured, traceable and maintainable.

---

## Foundation Principles

The Foundation was developed according to the following principles.

### 1. Engineering before Speed

The project should establish reliable structures before accelerating content production.

### 2. Structure before Scale

Growth should follow maintainable architecture.

### 3. Documentation as Product

Documentation should be designed, reviewed and maintained as a product capability.

### 4. Learning by Engineering

The Academy should combine concepts, practice, real cases and engineering reflection.

### 5. Traceable Decisions

Significant decisions should remain documented through ADRs, Decision Log entries and release records.

### 6. Controlled Evolution

Ideas may be accepted without requiring immediate implementation.

### 7. Maintainability

The project should only introduce structures it can reasonably support.

### 8. Institutional Continuity

Foundational documents should preserve the reasoning required for future contributors to understand the project.

## Foundation and Official Publications

Foundation documents and Official Publications serve different purposes.

### Foundation Documents

Preserve the initial project structure, review evidence and implementation context.

### Official Publications

Preserve formal institutional editions intended for publication and long-term reference.

Example:

```text
Foundation

Records how the institutional base was created and validated.

↓

Official Publications

Preserve the formal Manifesto, Vision, Mission, Core Values and Brand Principles.
```

A Foundation document may reference an Official Publication without duplicating its complete content.

---

## Foundation and Architecture

The Foundation collection preserves the initial project base.

The Architecture collection preserves decisions and structural models that continue to guide the project.

Example:

```text
Foundation

Explains why the initial structure was required.

↓

Architecture

Records the decisions and responsibilities of that structure.
```

Significant architectural changes should be documented in ADRs rather than only inside Foundation records.

---

## Foundation and Governance

The Foundation established the first Governance mechanisms.

Ongoing Governance belongs in the Governance collection.

The relationship may be understood as:

```text
Foundation

Establishes the initial Governance base.

↓

Governance

Maintains current decision, approval and change processes.
```

A current Governance rule should not depend only on a historical Foundation document when an active Governance document is more appropriate.

## Foundation Review

The Foundation Review evaluates whether the project base is sufficient for continued development.

Possible review dimensions include:

- institutional clarity;
- architectural consistency;
- repository organization;
- Governance;
- documentation quality;
- release readiness;

Foundation certification confirms that the project base was reviewed and considered sufficient for continued development.

## Acceptance Criteria

A Foundation stage may be considered complete when:

- project purpose is documented;
- institutional principles are visible;
- repository structure is defined;
- major architecture decisions are recorded;
- Governance mechanisms exist;
- document responsibilities are understandable;
- review evidence exists;
- release scope is documented;
- known limitations are visible;
- future work is sequenced;
- approval is traceable.

The exact criteria should remain connected to the Foundation Review and release documentation.

## Historical Integrity

Foundation documents should preserve historical context.

Do not rewrite them as though later decisions had already existed.

When a correction is required:

- preserve the original intent;
- identify the correction;
- update links;
- add context when necessary;
- avoid changing past scope silently.

Current guidance should be maintained in active Standards, Guides, Governance documents and Architecture records.

---

## Living and Historical Documents

The Foundation collection may contain both historical and current references.

### Historical Document

Preserves the state and reasoning of the Foundation period.

### Living Document

Continues to evolve because it remains an active project reference.

A document should clearly identify its status.

When a Foundation document becomes obsolete as current guidance, it may remain preserved for historical value while pointing readers toward its active replacement.

---

## Foundation Document Status

Foundation documents may use statuses such as:

### Draft

The document is being prepared.

### In Review

The document is undergoing validation.

### Accepted

The document has been approved for the Foundation stage.

### Completed

The document fulfilled its Foundation purpose.

### Superseded

A newer artifact replaced it as the current source of guidance.

### Archived

The document remains preserved for historical reference.

The applicable lifecycle should remain aligned with future lifecycle Standards.

## Repository Placement

A Foundation document belongs in this collection when it:

- establishes the original project base;
- documents Foundation-stage readiness;
- records Sprint 0 evidence;
- preserves initial project scope;
- explains the transition into continued development.

A document may belong elsewhere when it primarily defines:

- architecture;
- Governance;
- editorial requirements;
- learning content;
- technical procedures;
- release history;
- official institutional publication.

Repository placement should follow the artifact responsibility rather than its creation date.

---

## Avoiding Duplication

The Foundation collection should not duplicate complete content from:

- Official Publications;
- ADRs;
- Standards;
- Guides;
- Governance documents;
- release records;
- Roadmap documents.

Prefer references and relationships.

Example:

```text
Foundation Review

References ADR-0001 as evidence of repository architecture.

It does not copy the entire ADR.
```

This preserves a clear source of truth.
